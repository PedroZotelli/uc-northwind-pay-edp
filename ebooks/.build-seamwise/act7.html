THE EXITS · THE NUMBER IS PART OF THE CONTRACT

Exit codes separate human input from invalidity and conflict

Six numbers sort every outcome by who must act next: exit 2 asks a person for input, 3 and 4 reject invalidity and conflict, 5 names a missing host runtime, 10 owns the tool's own failure — and 0 means the command reached its intended boundary.

Success
0
The operation succeeded — or reached its intended ready boundary.
Human input
2
Evidence, ownership, decision, or review input is required — a person must move next.
Invalid
3
The command or the authored contract is invalid.
Conflict
4
Integrity, concurrency, filesystem, or topology conflict.
Host unavailable
5
A required host runtime is unavailable.
Mechanism failure
10
An internal mechanism failure — the tool, not the input.

THE DOCTOR · CORE, CODEX, CLAUDE, ALL

A missing host fails the host — never the core

doctor checks core health on every run and host health only for the selected host — layered rings, not one blended verdict.

Core ring · every run
  • platform
  • Python
  • package version
  • the result-envelope schema
  • Git
Host ring · selected host only
  • the host executable is present
  • the installed receipt and tree verify
  • a bounded live probe — only when explicitly requested
Missing host
A selected host that is not there returns exit 5 — the failure lands on the host ring and core state is not corrupted.
Platform boundaryNative Windows is unsupported — run Seamwise in a supported POSIX environment.

One question, one pass, one confirmation

The host conversation authors a recipe in five passes — each pass proposes its transformation, shows the complete result, and waits for confirmation before the next one runs.

The five rules
  • exactly one concise unanswered question at a time
  • show the complete pass, never a summary
  • wait for confirmation before moving on
  • run only the current transformation
  • never auto-review
